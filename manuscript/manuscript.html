Abstract

Smart contracts on public blockchains are immutable once deployed, so a code-level flaw can cause irreversible loss. We present a pre-deployment auditing prototype for Solidity. It compiles a contract, builds a multi-relational graph from its abstract syntax tree, control-flow graph and data-flow edges, slices the graph around security-relevant statements, and classifies it with a Graph Attention Network (GAT). The model gives a contract-level verdict and a node-level score that points to lines. The prototype covers three vulnerability classes: Reentrancy, Timestamp Dependency and Arithmetic Error. We evaluate it on six hand-written demo contracts, one vulnerable and one safe per class. The model fits its training contracts perfectly (18 of 18 class decisions correct). Under leave-one-contract-out evaluation, however, it flags none of the three held-out vulnerable contracts across five seeds (recall 0.000). A rule that flags any contract containing the relevant sink reaches recall 1.000 with precision 0.429. Logistic regression on pooled node features predicts "safe" throughout. We also found and fixed two code defects: training labels for two contracts that pointed at the wrong lines, and an arithmetic operator lookup that failed for legacy-format syntax trees. The results show that the pipeline runs end to end, that its in-sample fit does not generalize at this scale, and that a larger labelled benchmark is needed before any detection claim can be made.

Keywords: smart contracts; Solidity; graph attention network; program slicing; vulnerability detection; leave-one-out evaluation

1. Introduction

Smart contracts are programs that hold and move digital assets on blockchains such as Ethereum. Once deployed, the code cannot be patched, so a flaw can be exploited before its owner notices (Zheng et al., 2020). Two classes of flaw illustrate the stakes. Reentrancy lets a callee re-enter a function before the caller updates its state; this is the mechanism behind the 2016 TheDAO loss (Luu et al., 2016). Timestamp dependence lets a miner influence logic that relies on block.timestamp. Arithmetic errors wrap integers silently in pre-0.8 Solidity.

Automated tools address these flaws with symbolic execution, pattern matching or static analysis. Oyente runs symbolic execution on bytecode (Luu et al., 2016), SmartCheck checks Solidity source with extensible rules (Tikhomirov et al., 2018), and Slither lifts Solidity into an SSA intermediate representation (Feist et al., 2019). A large empirical review found that these tools disagree with each other, and that a high share of real contracts is flagged (Durieux et al., 2020). Learning-based detectors have been proposed as a way to reduce false alarms (De Baets et al., 2024), and graph neural networks are the most common choice because a contract's control and data flow is naturally a graph (Zhuang et al., 2020; Liu et al., 2023).

This project builds such a detector and asks three questions.

  • RQ1. Can a GAT over a sliced contract graph learn to separate vulnerable from safe contracts for the three classes?
  • RQ2. Does it generalize to a contract it has not seen, and how does it compare with simple baselines under the same protocol?
  • RQ3. Can its node-level scores localize the vulnerable line?

The contribution is the working pipeline, a leave-one-contract-out protocol with two baselines, a documented set of defects found and fixed during the work, and a negative result on generalization at this scale. We do not claim a detection rate.

2. Related work

Graph attention. The GAT layer computes attention coefficients over a node's neighbours and aggregates their features with those weights (Veličković et al., 2018). Graph convolution with a first-order spectral approximation is the simpler alternative (Kipf & Welling, 2017). The classifier here uses the GAT form.

Graph-based contract detection. Zhuang et al. (2020) build a graph of each function's syntactic and semantic structure, reduce it with an elimination step and apply a graph convolution with temporal message propagation. Liu et al. (2023) model contracts as a nested multi-relational graph of functions and localize vulnerable functions. Nguyen et al. (2022) use heterogeneous graph embeddings with metapaths for fine-grained detection. These methods are trained and tested on large corpora. The present work uses six contracts and is therefore a feasibility study.

Tool evaluation. Durieux et al. (2020) ran nine tools on 47,518 contracts and 69 annotated vulnerable contracts, and reported low agreement between tools and a high flag rate on real contracts. Ghaleb and Pattabiraman (2020) evaluated six tools by injecting bugs into contracts (SolidiFI). SolidiFI and the SmartBugs collection are natural held-out benchmarks for future work (Section 8). Sayeed et al. (2020) reviewed attacks and reported that the tools they tested still miss known flaws.

The earlier draft of this work cited six further papers that could not be verified against a publisher or arXiv record. They were removed. The verified literature is listed in LITERATURE_MATRIX.md in the repository.

The data are six Solidity files written for this project (Table 1). Each vulnerable file contains one minimal instance of its pattern. The Timestamp safe file is not a line-for-line variant of the vulnerable one. The files are not copies of deployed code. Labels are the author's annotations, checked by reading each file. 4. Method

4.1 Graph construction

The compiler wrapper (parser/compiler.py) reads the pragma, selects a solc version (0.7.6 or 0.8.20 in these experiments) and returns the AST. The graph builder (parser/graph_builder.py) creates a node for each AST node with its line and source text, an AST edge for each parent-child pair, control-flow edges from a statement walk, and data-flow edges from identifier references, assignments, declarations and call arguments. Both the legacy AST (solc 0.7.x, nodes labelled by name with children in children) and the compact AST (solc 0.8.x, nodeType with named fields) are handled.

4.2 Slicing

Interest points are external calls (.call, transfer, send), references to block.timestamp or now, and binary operators + - * /. From each interest point, the slicer follows control and data edges forward and backward for three steps, then adds up to three AST ancestors so the slice remains a connected tree (slicing/slicer.py). If a contract has no interest point, the seeds are function calls and variable declarations.

4.3 Model

Each node has a 25-dimensional feature vector: a one-hot code for its AST type over 20 types plus an "other" bin, and four keyword flags (call, timestamp, arithmetic, state write). Two GAT layers with hidden size 64 and a dropout of 0.1 produce node embeddings. A node head gives three per-class logits. A graph head applies to the mean of the node embeddings and gives three per-class logits. The graph loss is binary cross-entropy on the graph head, plus twice the same loss on the node head.

Training uses Adam with learning rate 0.005 and weight decay 1e-4, for 100 epochs with one optimizer step per graph. The seed is 42 for the saved weights. A class is flagged when its graph probability exceeds 0.5. A line is localized when a node in that line has a class probability above 0.3. Both thresholds were set by hand and were not tuned.

4.4 Evaluation protocol

With six contracts, a random split would leave no test positive for some classes. We use leave-one-contract-out (LOCO). For each held-out contract, the GAT is retrained on the other five and produces a verdict for each of the three classes. This gives 18 binary decisions per method (6 contracts × 3 classes), of which 3 are positive. The GAT is run with five seeds (0 to 4) to measure the effect of initialization and dropout.

Two baselines use the same folds:

  • Sink-presence rule. Flags a class whenever the full graph contains any sink for it. It uses the same keywords as the slicer and needs no training. It is the simplest rule that tests whether the learned model adds anything.
  • Logistic regression on the mean and maximum of the 25 node features over the sliced graph (50 values). It uses pooled features with no message passing, and tests whether graph structure is needed.

The in-sample result, which reuses the six training contracts, is also reported for comparison with the earlier draft. It is not a generalization result.

5.2 In-sample fit

Trained on all six contracts, the saved model gives 18 of 18 correct decisions (precision, recall and F1 all 1.000). Its confidences for the vulnerable contracts are 99.21% (Reentrancy), 99.99% (Timestamp) and 98.25% (Arithmetic). The highest confidence for any safe contract is 0.37%. This shows that the classifier can fit its training data. It says nothing about unseen contracts.

The GAT never flags a held-out vulnerable contract. Its accuracy of 0.767 comes from correctly predicting "safe" on most decisions, which the class imbalance rewards. 5.4 Node-level localization

For the saved, in-sample model, the auditor localizes Reentrancy to lines 15 and 16 (Figure 3), which are the external call and its result check. The Timestamp contract is localized to line 9, the require on block.timestamp. The Arithmetic contract is flagged at 98.25% but no line exceeds the 0.3 node threshold, so the auditor reports that it cannot localize it.

Under leave-one-contract-out, localization fails in all 15 vulnerable-contract evaluations (3 contracts × 5 seeds): no node reaches the threshold for the held-out contract's class. The mean precision and recall are both 0.000.

7. Discussion

RQ1 (fit). The GAT learns its six training contracts perfectly and gives high confidence to the correct class. Learning the training data is therefore not in question. The question is what it learned.

RQ2 (generalization). Under leave-one-contract-out the GAT does not generalize. The reason is structural and not a matter of tuning. Each class has one positive and one negative contract, so holding out a contract removes the only positive for its class. The model then has to infer a pattern from a single example, and in our folds it infers the wrong one. In this setting the learned model did not beat the fixed rule, which had higher recall. The sink-presence rule's precision of 0.429 is also a warning: a learned model that just reproduces the rule would add nothing.

RQ3 (localization). Localization works in-sample for the Reentrancy and Timestamp contracts. Under leave-one-out it fails in every fold, because the node scores depend on the same class signal that the classifier cannot learn from one example. The localization result therefore depends on the training set and should not be read as a property of the architecture.

What the defects show. Both code defects (the label offsets and the legacy operator lookup) survive an in-sample check, because the in-sample check reuses the same labels and graphs. The operator bug removed the only arithmetic sink from a legacy-syntax contract, so the arithmetic class had no arithmetic seed in that graph. This suggests that in-sample checks do not catch input-handling bugs, and that tests for each syntax format are needed. We did not test this beyond the one contract.

8. Limitations

  1. Six contracts. Three positive and fifteen negative class decisions cannot support precision or recall estimates with any confidence. A single decision changes the sink rule's precision by roughly 0.07 to 0.14.
  2. Keyword features. Flags are set by substring matches. "now" matches inside words such as know, and "send" matches inside msg.sender. The sink-rule errors above show that these substrings produce false signals. An ablation to measure their effect on the GAT has not been run.
  3. Hand-set thresholds. The 0.5 graph and 0.3 node thresholds were not tuned on held-out data.
  4. Narrow compiler coverage. Solc 0.7.6 (legacy AST) appears in one contract. Versions 0.4.x to 0.6.x are mapped but untested.
  5. Only one GNN variant. The TMP and MRN-GCN variants described in the earlier draft are not implemented.
  6. No public benchmark. SmartBugs and SolidiFI are the natural held-out sets (Durieux et al., 2020; Ghaleb & Pattabiraman, 2020). Using them requires a separate decision about downloading them, which was not made for this report.
  7. No calibration. The reported confidences are sigmoid outputs and have not been checked against observed frequencies.

9. Conclusion

We built and tested a pipeline that turns Solidity contracts into multi-relational graphs, slices them, and classifies them with a GAT. On six demo contracts it fits its training data exactly and points to the Reentrancy call and its check. Under leave-one-contract-out evaluation it does not detect any held-out vulnerable contract, and a fixed sink-presence rule has higher recall. The pipeline is a reproducible starting point, not a detector. The next step is the held-out evaluation on SolidiFI and SmartBugs with precision, recall and F1 reported on contracts the model has not seen, and with comparison against the tools named in Section 2.
